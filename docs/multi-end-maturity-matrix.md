## 二、维度横切诊断

### 存储维度（整体 ✅ 偏强）
- **强**：IDB 模型库、句柄持久化、键命名空间、清单存储均已落地。
- **弱**：① FSA 多选同名 PMX 撞车（ADR-182 未覆盖，待评估）；② IDB 按 origin 隔离 → `localhost:5173` 与 GitHub Pages 数据不共享，删库需重选目录（**已文档化**：`docs/web-data-origin-isolation.md`）。

### 权限维度（中等，架构性负债）
- **强**：FSA 授权/重授权、句柄持久化、能力声明（watchDir）已铺开。
- **弱**：缺统一的「端能力协商协议」。现状是每新增能力就在 adapter 加一处 `isAndroidPlatform()` 分支（ADR-178 即是补丁式），接缝随能力数增长而变脆。

### 更新维度（全局最弱）
- 唯一卡点集中在 ADR-179：阶段 1 安卓优先拉起已通；阶段 2 桌面 `DownloadAndRunInstaller` 仍仅伪代码，production 未实现；Web 端「不动」为设计取舍但也是能力缺口。
- 这是目前唯一阻断「桌面端自助更新」的硬卡点。

### 验证维度（守护不足）
- **强**：单测覆盖好（85/85、25、14/14、契约 139）。
- **弱**：跨端行为一致性缺少自动化守护。ADR-177 的 CI 线上 smoke / browser E2E 已降为日常回归跟踪；桌面 E2E（尤其更新链路）基本空白。

## 四、总体结论
多端统一的「骨架」已立（双 adapter + 统一 web 入口 + 能力层宿主感知），卡点集中在**更新闭环**与**权限协商协议化**两块。前者是单点交付缺口，后者是架构性预防负债。二者皆非炸雷，但建议优先把 P1 两项并入下一轮议会决议。
